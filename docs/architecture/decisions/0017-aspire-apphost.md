# 0017. Aspire runs the local environment, and LAN mode shows it to another machine

Date: 2026-11-13. Status: accepted.

Issue #55. The owner wanted one command that brings up the app and its API
reference, with links that work from his own machine on the LAN, and asked
for Aspire, the way void-crm already runs (its ADRs 0008 and 0015).

## Decision

- **One TypeScript AppHost, `apphost.mts`, at the root**, with
  `aspire.config.json` (Aspire 13.5.3, `Aspire.Hosting.JavaScript`) and
  `tsconfig.apphost.json` beside it: void-crm's layout. The SDK under
  `.aspire/` is generated by every `aspire start` and git-ignored. No .NET
  SDK is needed; the AppHost's own packages (`tsx`, `vscode-jsonrpc`) are root
  devDependencies, so `npm ci` is the only install. `apphost.mts` is
  type-checked by Aspire before each start, not by `npm run typecheck`,
  because its imports are the generated SDK, which CI does not have.
- **Four resources.** `web` runs apps/web's own vite as `vite build --watch
  --no-emptyOutDir` (#34, #43), so its build output has its own log. `api`
  runs `scripts/aspire-api.mjs`, which applies the D1 migrations, waits for
  web's first `index.html`, then runs `wrangler dev` on the port and
  inspector port Aspire hands it; it is healthy when
  `GET /api/events/reinvent2026` answers. `seed` waits for api and runs
  `npm run seed:demo`. `lan` exists only with `HALLWAY_LAN=1`.
- **Ports are Aspire's and state is the worktree's**, as in void-crm ADR
  0015: `aspire start --isolated`, nothing in `apphost.mts` names a port
  (except LAN mode, below), and D1, wrangler's dev registry and its logs live
  under `.state/` (git-ignored). Deleting `.state/` resets the data.
  `npm run dev` is unchanged and still keeps its own D1 under
  `.wrangler/state`; the e2e suite does not use either.
- **The seed is idempotent through the public API alone.** Dev sign-in by
  name finds the same attendee each time (ADR 0008); a schedule sync makes
  the synced entries equal the lists given; connecting from a share link
  answers with the connection, new or existing; the invite is made on first
  ask. So the seed runs on every start, and a second run changes nothing
  (`apps/api/src/seed-demo.test.ts` runs it twice). Its data: four people,
  the owner as "Blake Hastings" among them, with schedules from the
  AWS-shaped fixtures the API and e2e tests use, and three connections.
- **The API reference is in the product**: `GET /api/docs` on the Worker is a
  Scalar viewer over `/api/openapi.json`. Scalar's standalone bundle is
  `@scalar/api-reference@1.76.2` from jsDelivr, pinned, with a
  Subresource Integrity hash, so a changed CDN file is refused by the
  browser. The dashboard links it from the api resource.
- **LAN mode** (`HALLWAY_LAN=1 npm run aspire`), for an owner on another
  machine:
  - *The app* goes through `scripts/lan-proxy.mjs` on `0.0.0.0`, which
    forwards to wrangler with the Host header set to wrangler's own loopback
    address and rewrites a redirect back to that origin onto the address the
    browser used. Dev sign-in and the non-Secure cookie on plain http both
    require a loopback host (ADR 0008), and this keeps that rule as it is
    rather than loosening it for the LAN. wrangler itself still listens on
    127.0.0.1 only.
  - *The dashboard* listens where `ASPNETCORE_URLS` says. `scripts/aspire.mjs`
    sets it to `http://0.0.0.0:<port>` with
    `ASPIRE_ALLOW_UNSECURED_TRANSPORT=true` (the dashboard refuses plain http
    otherwise), and Aspire's proxy then answers on every interface.
  - *The dashboard keeps its sign-in.* Its browser token is new on every
    start; `npm run aspire` prints the login URL with the LAN host and that
    token (`/login?t=...`), which sets the dashboard's cookie. Rejected:
    `ASPIRE_DASHBOARD_UNSECURED_ALLOW_ANONYMOUS`, which would let anyone on
    the network stop and start resources, and read every log.
  - *Two ports are fixed*, so a bookmark survives a restart:
    `HALLWAY_LAN_PORT` (default 8796) for the app and
    `HALLWAY_LAN_DASHBOARD_PORT` (default 8797) for the dashboard. The links
    use this machine's first non-internal IPv4 address; `HALLWAY_LAN_HOST`
    overrides it.

## Consequences

- From another machine, `npm run aspire` in LAN mode gives working links for
  the app, the API reference and the dashboard; the owner signs in as
  himself with dev sign-in and sees seeded data.
- Through the LAN proxy the Worker believes it was asked on 127.0.0.1, so a
  URL it builds from the request (share links, link-preview tags) names
  127.0.0.1. Signing in and every page work; copying a share link from a LAN
  browser does not. The fix, if needed, is an `X-Forwarded-Host` the Worker
  reads only when dev sign-in is allowed.
- Plain http on the LAN: the dashboard token and the session cookie cross
  the network unencrypted. Acceptable for a home LAN and a dev tool; LAN
  mode is never on unless asked.
- Telemetry from workerd does not reach the dashboard (void-crm found the
  same); its logs do, through the console log view.
- Rejected: Vite's dev server as the web resource (ADR 0010: it serves
  `/@...` paths itself and tests a routing setup production never runs);
  `addJavaScriptApp` and `addViteApp` (they add an `npm install` resource,
  and `addViteApp` runs the dev server); making `npm run dev` start Aspire
  (agents building slices use it, and it needs no Aspire CLI).
